# Bacchus Task Planner

Decompose a goal into a `.bacchus/tasks.yaml` file optimized for parallel agent execution.

## Arguments

`$ARGUMENTS` contains the goal to decompose.

## Steps

### 1. Understand the Codebase

Index and search for relevant code:
```bash
bacchus index src/
bacchus symbols --search "<relevant terms>" --handle
bacchus handle expand <handle> --limit 10
```

Read key files to understand architecture before planning tasks.

### 2. Design the Task Graph

Principles:
- **Maximize parallelism** — only add `depends_on` when a task truly needs another's output
- **Non-overlapping footprints** — concurrent tasks must not touch the same files/symbols
- **Right-sized tasks** — each task should be completable by one agent in one session
- **Clear boundaries** — each task owns specific files/symbols via its footprint

**Parallelism ratio rule (CRITICAL):** Count tasks with empty `depends_on`. This ratio MUST be ≤50% of total tasks. If it exceeds 50%, you MUST add explicit dependencies — likely some tasks depend on shared setup, schema, types, or interfaces that should be sequenced first. Do not proceed to writing tasks.yaml until the ratio is ≤50%.

**Footprint rule (CRITICAL):** Every footprint entry for an existing file MUST use symbol-level references (`src/file.rs::SymbolName`). Bare file references (`src/file.rs`) are ONLY allowed when:
1. The file is being newly created (listed under `creates:`)
2. The entire file is being restructured/replaced

Before writing any footprint entry, ask: "Does this file already exist?" If yes, you MUST use `src/file.rs::SymbolName` or `src/file.rs::*`, never a bare `src/file.rs` under `modifies:`.

### 3. Write tasks.yaml

```yaml
tasks:
  - id: <PREFIX>-001
    title: "<imperative description>"
    description: |
      <What to implement and why.>
      gate: <specific condition that must be true for this task to be done, e.g., "all tests in tests/auth/ pass", "cargo check --quiet exits 0", "endpoint returns 200 for valid input">
    task_type: feature|bug_fix|refactor|test|docs|infra|generic
    archetype: design|frontend|backend|data|test|infra|review|security|generic
    depends_on: []
    footprint:
      modifies:
        - "src/file.rs::SymbolName"   # REQUIRED: use symbol-level for existing files
      creates:
        - "src/new_file.rs"           # bare path allowed only for new files
```

**Description requirements:**
- Every task description MUST end with a `gate:` line specifying the verifiable done-when condition
- Examples: `gate: cargo test auth passes`, `gate: visual diff against spec approved`, `gate: bacchus validate exits 0`
- Acceptable keywords: `gate:`, `done when:`, `verify:`, `must pass:`

**Footprint requirements:**
- **Default to symbol-level** (`src/file.rs::SymbolName`) for all existing files — this is the expected format
- Use `src/file.rs::*` when a task owns all symbols in a file but the file already exists
- Use bare `src/file.rs` **only** under `creates:` (new files) or when restructuring an entire file
- Listing an existing file as a bare path under `modifies:` is a footprint quality failure

Footprint syntax:
- `src/file.rs` — entire file (only for new/restructured files)
- `src/file.rs::Symbol` — specific symbol (default for existing files)
- `src/file.rs::*` — all symbols in existing file
- `src/dir/*.rs` — glob

### 4. Validate

```bash
bacchus task import --epic-id <EPIC_ID>
bacchus task list --ready
bacchus task validate
```

Fix any validation errors (overlapping footprints, missing deps, invalid symbols).

**Self-check before finalizing:**
1. Count tasks where `depends_on` is empty. Is the ratio ≤50%? If not, add dependencies.
2. Scan every `modifies:` entry. Does any line reference an existing file without a `::Symbol` qualifier? If so, fix it.

### 5. Output

Print a summary:
- Total tasks, how many can run in parallel initially (and the ratio — must be ≤50%)
- Critical path (longest dependency chain)
- Recommended `--max-concurrent` value
